# Supabase Dashboard roadmap

Updated: 2026-11-13

## Goal and status

Build a self-hosted dashboard in Rust that works like <https://supabase.com/dashboard>: you sign in to the dashboard, pick an organization and a project, and the project opens in that stack's own Supabase Studio. Nobody reaches a project's Studio without signing in to the dashboard. The dashboard adds what self-hosted Supabase lacks: organizations and members, a registry of many stacks, access control for their Studios, health, provisioning, configuration, and servers.

Repository: <https://github.com/FilipNone/supabase-dashboard>.

Status (2026-11-13): M0 to M3 are complete, which covers the P1 scope of the first usable release. M4 (project lifecycle) is in progress: the Dokploy provider has a disposable test instance, a version check, and an installation-level connection that installation admins manage. Earlier summary: a Cargo workspace exists with an Axum server, Leptos SSR/hydrated UI shell, control-plane PostgreSQL migrations, and CI (see `docs/development.md` and `docs/adr/0001-stack-and-workspace.md`). Operators can be bootstrapped from the command line, sign in and out, edit their profile, change their password, and sign out other sessions. Installation admins can list accounts, disable or re-enable them, and see every organization and registered project. Every page and API path requires a session, except the invitation page. Operators can create and rename organizations, switch between them, and manage member roles, removal, and leaving from the browser. Owners and admins can invite people by email; the invitee accepts with an existing account or creates one from the link. Owners and admins can register an existing stack as a project by its API URL, rename it, change its API URL, and unregister it; every member can see the organization's projects. Owners and admins can store a project's anon and service role keys, encrypted on the server, and any member can run a health check that reports whether the stack's Auth and REST services answer, with the Auth version. The read-only table editor, SQL editor, and saved snippets built earlier were removed on 2026-11-10, because a project's pages are its own Studio (`docs/adr/0002-studio-access.md`). An installation admin can confirm which Dokploy service the dashboard runs as, found by its public domain. An installation admin can choose which Dokploy environments and servers each organization's new stacks may go to. Owners and admins can create a new stack through Dokploy as a durable job, and a provisioned project's overview shows its Dokploy service as Dokploy reports it, where owners and admins can stop, start, redeploy, remove it, and change its settings, and owners can destroy it with its data. Current focus: the Dokploy provider in M4.

Priority scale: P1 = required for the first usable release; P2 = next release after the foundation; P3 = later or dependent on research. Milestones indicate dependency order, not dates or delivery estimates.

## Scope decisions

- The primary target is a browser-based application with a Rust backend and Rust UI compiled to WASM where needed. HTML/CSS and generated browser bootstrap code are allowed. No native desktop shell is planned.
- Evaluate Axum/Tokio, Leptos SSR/WASM, and SQLx/PostgreSQL in M0. Framework choice and exact versions remain provisional until a buildable proof of concept is checked.
- Keep the dashboard's identity, organization membership, project registry, and job state in its own metadata database. Managed project outages must not prevent dashboard login.
- One dashboard project initially maps to one self-hosted Supabase stack. Multiple projects require multiple registered stacks, not a nonexistent self-hosted organization API.
- Import and inspect existing stacks before provisioning new ones. Local/remote deployment ownership must be explicit; removing a registry entry must never imply deleting its database or volumes.
- Supabase's hosted Management API is unavailable in self-hosted installations. Use verified PostgreSQL, postgres-meta, service APIs, and deployment-provider integrations behind server-side adapters. Discover capabilities instead of assuming cloud API parity.
- Hosted billing is out of scope. Branching, PITR, cloud metrics, and other managed services require separate infrastructure and are not implied by visual parity.
- Dashboard SSO authenticates operators. Configuring a managed project's end-user Auth providers is a separate feature with separate credentials and permissions.
- A project's pages are the stack's own Supabase Studio, reached through the dashboard (`docs/adr/0002-studio-access.md`). The dashboard does not rebuild Studio's table editor, SQL editor, database, Auth, Storage, Realtime, Functions, or logs pages. Each project's Studio is served on its own host under a domain the deployment chooses, because the stock Studio image only runs at the root of a host. The dashboard signs the member in, checks their role, and forwards their requests to the stack's gateway, adding the gateway's Studio password on the server.
- Studio has no roles of its own: anyone who opens it can run any SQL as the database owner and read the stack's keys. Only roles meant to have that power may open Studio (owners, admins, developers). Viewers see the project's status in the dashboard only.

## Roadmap review

The original list covered account/organization pages and integrations but had no implementation order or acceptance criteria. An earlier revision of this plan added project-level database, SQL, Auth, and Storage pages to the dashboard itself. That was a mistake in the plan: every self-hosted stack ships Studio with those pages. The 2026-11-10 revision replaces them with access to the stack's own Studio.

The main technical risks are privileged credentials, isolation between organizations and between projects' Studios, the Studio gateway that carries all Studio traffic, remote-target SSRF, and recovery from partially completed infrastructure changes. Address these before exposing mutations. The reference dashboard's authenticated pages have not been visually verified in this review; the route list is a compatibility target, not a claim about its current exact routing or feature availability.

### M1: accounts and organizations (P1)

- [x] Implement secure initial-owner bootstrap, login/logout, account editing, and session revocation. Disable public registration by default. (Done: `create-owner` bootstrap that refuses to run twice and never takes the password as an argument; email/password sign-in with Argon2id; sign-out; hashed session tokens with absolute and idle expiry; no public sign-up. Account settings at `/dashboard/account/me` and `/dashboard/account/security`: operators change their display name, change their password after confirming the current one, list their live sessions, and sign out any other session or all of them. A password change signs out every other session in the same transaction, and wrong current passwords count toward the sign-in throttle. Changing the sign-in email is not supported yet.)
- [x] Define organization/project permissions and test an initial owner/admin/developer/viewer role matrix server-side. (Done: the matrix and last-owner rule live in `crates/domain/src/authz.rs` with exhaustive unit tests. `OrganizationService` checks them on every organization and membership operation, with database-backed tests for each role. `ProjectService` applies the same matrix to registering, renaming, changing the URL of, and unregistering projects, with database-backed tests per role. Table tests run owner, admin, developer, viewer, and a non-member through role changes, member removal, invitations and their withdrawal, project rename and URL change, API key removal, Studio access, and the Studio access log and its export, checking that each refusal leaves the target unchanged and is audited. Non-members get the same not-found answer as for an unknown ID and are not audited.)
- [x] Add organization creation/editing, switching, invitations, membership removal, and last-owner protection. (Done: application service and storage for creating and renaming organizations, listing members, changing roles, removing members, and leaving. Membership changes lock the organization row, so concurrent demotions cannot remove the last owner. The browser UI has an organization list with a create form, a General tab for renaming, a Team tab for role changes, removal, and leaving (each removal behind a named confirmation), and a top-bar switcher. Invitations: owners and admins create them on the Team tab for an email and role (only owners can invite owners) and can withdraw open ones. Each invitation has a 256-bit code that is stored only as a SHA-256 hash, expires after 7 days, and works once, only for the invited email. The link carries the code in the URL fragment, and the acceptance page removes it from the address bar. Someone with an account signs in and accepts; someone without one creates an account from the link, which never makes them an installation admin. Until dashboard email delivery exists, the inviter copies the link, which is shown once. Known gap: an invitee who has to sign in first must open the link again afterwards.)
- [x] Implement dashboard account security and an initial administrator view for users and registered resources. (Done: installation admins can list dashboard accounts and disable or re-enable them, which revokes their sessions and is audited. The same page lists every organization with member and project counts and every registered project with its organization and API URL, up to 500 of each with a note when more exist. The list is read-only and grants no access: an admin who is not a member of an organization still cannot open its projects. Refused attempts to load it are audited.)
- [x] Add audit events for security-sensitive actions and admin changes, with secret redaction. (Done: owner bootstrap, sign-in success and denial, sign-out, session revocation, profile changes, and password changes (including refused attempts) are recorded with actor, target, outcome, and request ID and no credentials. Refusals are recorded too: a repeated owner bootstrap, a password reset for an unknown email, an administrator disabling their own account or the last administrator, revoking a session ID that is not the caller's, signing up with or accepting an invalid invitation code (the code is not stored), creating an organization or registering a project past its limit, opening Studio when no usable login is stored, and reading the Studio access log without permission. As of 2026-11-12 every operation in `crates/application` that changes an account, session, organization, membership, invitation, project, stored key, Studio login, or certificate writes an event, and so do the administrator's account and resource lists, opening Studio, reading and exporting the Studio access log, and re-encrypting keys from the command line. A used or expired Studio handoff code is not recorded: that path has no session, so anyone could fill the audit table with it, and the code alone opens nothing. Features added later record their own events.)
- [x] Add CSRF protection, login rate limits, secure cookies, and cross-organization access tests. Establish a tested recovery path for the chosen login method. (Done: `Sec-Fetch-Site`/`Origin` check on every unsafe request, `__Host-` HttpOnly SameSite=Lax cookie over HTTPS, per-email failure throttle. The throttle is in memory, so it is per server process. Cross-organization tests cover the organization service: a non-member gets the same not-found answer for another organization's ID as for a made-up one. An HTTP test signs in two operators and checks that one cannot read or rename the other's organization through server functions or the page, and that a cross-site rename with a valid cookie is refused. Recovery: the `reset-password` server command sets a new password for an account and signs it out everywhere; it needs the same server and database access as owner bootstrap and is tested at the application level.)

Acceptance: two organizations cannot read or mutate each other's records, including through guessed IDs and job/download endpoints. Disabled users and revoked sessions lose access. Invitations expire and cannot be reused (covered by application and HTTP tests). Default/bootstrap credentials cannot remain active unnoticed.

Owners and admins can also store a project's own certificate authorities on its settings page. They are checked to hold only usable certificates (at most 8, no private keys), listed with subject, expiry, and SHA-256 fingerprint to every member, audited when changed, and trusted only for that project's health checks, Studio login check, and Studio traffic, on top of the shared roots. - [x] Detect reachable services, component versions, permissions, and supported capabilities; distinguish unknown health from failure. (Done: a check asks the gateway for Auth health with the anon key, the PostgREST root with the service role key, Storage's version path, Realtime's ping, and the Edge Functions router with the anon key, and Studio's route with the stored login. It records healthy, key rejected, not found (the gateway has no route for the service), no route (the request reached the gateway's Studio login instead, so the key was never checked), HTTP error, unreachable with a fixed reason, or not checked because a key is missing or unreadable. The Auth and Storage versions are read from their responses, and the PostgREST version from its `Server` header when the gateway passes it on, or else from the start of its OpenAPI description. Verified against the fixture through both Kong and upstream's default Envoy gateway, with the HS256 keys and, through Envoy, the opaque `sb_publishable_` and `sb_secret_` keys. The server also checks every project on its own, by default when its last check is more than 15 minutes old (`SUPABASE_DASHBOARD_HEALTH_CHECK_INTERVAL_MINS`, 0 turns it off), at most 20 projects a minute and 4 at a time. Each pass claims its projects for 10 minutes first, so server processes sharing a metadata database split the checks rather than each checking every project. The Edge Functions check asks the router for no function at all, so no function runs; the router's own "not found" answer counts as healthy and a gateway 404 does not. Each key is checked where its role matters: the anon key on Auth, and the service role key on the PostgREST root, which both gateways refuse to the anon key with 403, so a service role field holding the anon key shows as rejected. Keys pasted into the wrong field are refused when saved, by their `role` claim or their `sb_` prefix. `docs/supabase-compatibility.md` is the service and version matrix, with the test behind each row, and each project's health table marks the reported Auth, PostgREST, and Storage versions as tested, older, newer, or not comparable. Analytics is not checked: upstream 0.8.4 runs Logflare only in its `docker-compose.logs.yml` overlay, Kong's analytics route is commented out, and Envoy has none, so the dashboard has no way to reach it through the gateway. Studio talks to it over the stack's internal network, and Studio's logs pages show whether it works.)
- [x] Show project cards, project overview, service health, and connection diagnostics. Support metadata edits and explicit credential replacement. (Done: the organization page lists project cards, and each project has an overview and a settings page where it can be renamed or pointed at a new API URL (same checks as registration, audited, and nothing is sent to the stack). The overview shows the last saved health check with its time and a Check now button, rate limited to one check per project every 10 seconds. The settings page has the API key section. Over HTTPS the overview also shows when the gateway's TLS certificate expires, flagged 30 days ahead and once it has passed; project cards and the administrator's project table carry the same warning, counted from the time the page is read, and the administrator page counts the projects that have one. Each failed service says where to look next: a gateway 502 to 504 points at the service's container, a 500 at its logs, a TLS failure at the project's certificate authorities, and a DNS failure at the API URL and the server's resolver. The overview also lists each service's address for client setup. `an_outage_shows_and_clears_without_touching_other_projects` checks that a stack that goes down shows as unreachable, that the next check after it comes back is healthy with the failed check kept in the history, and that another project in the same organization is unaffected.)
- [x] ~~Implement schema/table/column browsing and read-only data access.~~ Dropped on 2026-11-10: Studio's Table editor does this. The read-only table editor built for it was removed.
- [x] Add disconnect/unregister behavior that preserves the remote stack and its data. (Unregistering requires typing the project name and deletes only the registry row. Nothing is sent to the stack.)
- [x] Test forbidden destinations, redirects/DNS changes, expired credentials, unreachable services, permission errors, and unsupported versions. (Done: adapter tests cover refused loopback, names resolving to loopback, cloud metadata addresses, redirects not followed, timeouts, oversized bodies, closed ports, TLS failure, and rejected keys. A correctly signed key whose `exp` has passed is reported as rejected through both gateways. Every resolved address is checked at connection time. Pasted JWT keys are refused when their `role` claim belongs in the other field or their `exp` claim has passed, and the settings page shows each stored key's expiry, flagged 30 days ahead; the claims are read without verifying the signature. Nothing is refused by version yet, because the dashboard's only operations on a stack, the health check and Studio forwarding, do not depend on service versions and no version is known to break them. Refusing untested versions belongs with the first version-dependent operations: the Dokploy version check and stack configuration changes in M4.)

Acceptance: an operator registers a disposable stack, sees its health, and reconnects after a service outage without affecting other projects. Secrets never appear in browser responses or logs. Unregistering leaves the stack intact.

### M4: project lifecycle and remote servers (P2)

- [ ] Define a deployment-provider interface and implement one documented provider first. Dokploy is the first provider (see "Dokploy integration" below); a separate Docker/SSH executor comes after it.
- [ ] Add enrolled remote servers with verified identity, connectivity checks, access restrictions, and resource inventory.
- [ ] Provision a new isolated stack through a durable background job with generated secrets, health checks, progress, and reconciliation after restart.
- [ ] Edit supported stack configuration with a preview, validation, restart requirements, and recovery instructions. Refuse a change on service versions it was not tested with, and say which version was found.
- [ ] Separate project unregister, stack removal, and data/volume destruction in both permissions and UI; document backup prerequisites.
- [ ] Document and test metadata backup/restore. Add provider-aware project backup/restore only after an isolated restore drill succeeds.

#### Dokploy integration (first M4 provider, P2)

Goal: when the dashboard is installed as a service on [Dokploy](https://dokploy.com), it finds that Dokploy instance and its own place in it. Every Supabase stack it creates then appears in Dokploy as a Compose service, in the same Dokploy project and environment as the dashboard unless the operator picks another one.

What the Dokploy documentation says (read through Context7 on 2026-11-08; check again against the version we pin):

- The API is served at `/api/<router>.<procedure>` and authenticated with an `x-api-key` header. A key belongs to one Dokploy user and one Dokploy organization (`metadata.organizationId`), has that user's permissions, and can have an expiry.
- Resources form a tree: organization, project, environment, service. Each project starts with a default environment, and services in different environments are isolated from each other. Members can be limited to specific projects and environments.
- `compose.create` takes a `name` and an `environmentId`, plus optional fields that include `serverId` (deploy on a remote server) and `composeType` (`docker-compose` or `stack` for Swarm). Older API versions took a `projectId` instead, so the supported version range matters.
- Other calls we need: `project.all`, `environment.byProjectId`, `environment.create`, `compose.one`, `compose.update`, `compose.deploy`, `compose.delete` (with a required `deleteVolumes` flag), and `domain.create` (with `composeId` and `serviceName`). `compose.deployTemplate` deploys the official templates.
- Environment variables set on a service are written to its `.env` file and reach containers only where the compose file references them. Project and environment shared variables are referenced as `${{project.NAME}}` and `${{environment.NAME}}`.
- "Isolated deployments" put each compose app on its own network named after its `appName` and attach Traefik to that network. Without isolation, two stacks with the same service names collide on the shared `dokploy-network`.
- The official Supabase template routes one domain to an Envoy `api-gw` service on port 8000. The health check and the Studio gateway are verified against upstream's Envoy config (fixture port 54323), with both the HS256 keys and the opaque `sb_` keys.
- The docs describe no variable that tells a container its own Dokploy project, environment, or service. Detection has to be built (first item below).
